Verifying the systolic array accelerator

How I tested the reconfigurable systolic array accelerator and its RISC-V core.

SystemVerilog testbenches, ModelSim

I tested every part of the design in simulation, from a single grid of processing elements up to the whole system running real firmware. Each testbench compares the hardware with a reference I wrote separately from the RTL, so a bug would have to be made twice, in exactly the same way, to slip through.

Two references written on their own

A test is only as good as the answer it compares against. I wrote two reference models without looking at the RTL:

  • An arithmetic model that does each multiply-accumulate exactly the way the hardware should, including how each 8-bit lane wraps around. It catches a carry leaking from one lane into the other, not only a wrong total.
  • An instruction-set model of RV32I, written from the RISC-V manual. It runs next to the processor and works out what every instruction should do.

The array

The first testbench drives the grid of PEs directly. It loads random matrices, runs them in all three dataflows and both precisions, and compares every result that comes out of the bottom of the array with the reference. Each combination runs once normally and once with the array paused at random moments, to show that a pause never changes the answer. It also runs two jobs back to back without a reset in between.

One test fills every input with the most negative number, so each product is as large as it can be and the running totals reach the top of their spare bits. The array is also tested at 3×5, not only 4×4. In a square array, rows and columns are easy to mix up without any test noticing.

The accelerator

The second testbench plays the part of the processor. It writes the matrices into the buffers the way a driver would, sets up and starts the job, polls the status register, reads the results back, and compares them with A × B from the reference. It covers:

  • every dataflow and precision, with random lengths and the full 512-row depth
  • the largest possible values
  • random pauses on about one cycle in four
  • jobs back to back with no reset
  • the cycle count: without pauses, every job must take exactly the number of cycles the design predicts
  • the write lock: during each job it tries to overwrite the settings and the buffers, then checks that nothing changed
  • bad setups, like a length of zero, which must raise the error bit and never start

The address map is typed out by hand in the testbench instead of reusing the constants from the RTL, so a mistake in the map itself would show up too.

The processor

The core is checked in lockstep with the instruction-set model. Every time the core finishes an instruction, the model runs the same one, and the testbench compares the program counter, the instruction, the register written and any memory access. The model keeps its own copy of memory, so a wrong store is caught at the store itself, not later when something reads it back.

Three kinds of programs run through it:

  • A self-checking test of all 40 instructions and their corner cases, 939 instructions long. It took exactly 939 cycles, which confirms one cycle per instruction.
  • 30 fault cases: illegal instructions, misaligned loads and stores, jumps to bad addresses, accesses to addresses nothing answers, and a few look-alikes that must not fault. Each real fault must stop the core on the right instruction with nothing written.
  • 150 random programs of 300 instructions each.

The test memory adds random delays and puts junk on the data lines until the real data is ready, so a core that uses its data too early gets caught.

The whole system

The last testbench runs the real firmware on the full system: processor, memories, bus and accelerator. Every instruction is still checked against the model, about 2.3 million per run. After each job, the testbench reads A, B and C out of memory and checks that C = A × B with its own arithmetic. The jobs cover all three dataflows, both precisions, matrix sizes that don't divide evenly into tiles, the largest values, a 1×1×1 multiply, and a setup the accelerator must refuse. The whole run is repeated on a 4×4 and a 3×3 array.

Do the tests actually catch bugs?

Passing tests only mean something if they would fail on a broken design. To check, I put bugs into a copy of the RTL one at a time and ran the tests again. Some of them:

Planted bugCaught by
The wait after streaming is one cycle too shorttb_accel
The router sends A instead of B in input stationarytb_accel
8-bit results lose their signtb_accel
The accelerator accepts writes while a job runstb_accel
Rows and columns swapped at the bottom of the arraytb_pe_array, only at 3×5
Subtract runs as addtb_rv32i_core
Register x0, which must always read 0, can be writtentb_rv32i_core
The bus sends the accelerator's read signal twicetb_soc

Every bug planted in the accelerator was caught. In the processor, 16 of 18 were caught on the first try. The two that got through pointed at real gaps: no test took a branch or jump longer than 2 KB, and the test memory never handed back bad data while a load was waiting. I added long jumps in both directions, made the test memory show junk until its data is ready, and added loads that use their own destination register as the address. Now all 18 are caught.

Code

All six files are in the tb folder:

  • tb_ref_pkg.sv The arithmetic reference model, shared by the array and accelerator tests.
  • tb_rv32i_iss_pkg.sv The RV32I instruction-set model and the lockstep checker.
  • tb_pe_array.sv The array test.
  • tb_accel.sv The accelerator test.
  • tb_rv32i_core.sv The processor test: instruction test, fault cases and random programs.
  • tb_soc.sv The whole-system test running the firmware.
