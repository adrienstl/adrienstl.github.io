Reconfigurable systolic array accelerator

Personal project, 2026.

SystemVerilog, RISC-V (RV32I), ModelSim, Quartus Prime, Cyclone V FPGA

A hardware accelerator for the matrix multiplications that make up most of the work in a neural network, plus a small RISC-V processor I wrote to drive it. Software decides how data moves through the accelerator and whether it works on 16-bit or 8-bit numbers, using nothing but ordinary load and store instructions.

How a systolic array works

A systolic array is a grid of small identical units called processing elements (PEs). Each one multiplies two numbers, adds the product to a running total, and passes its values to its neighbours on the next clock cycle. Data enters at the edges and moves through the grid like a wave, so every number read from memory is used by a whole row or column of PEs instead of just one.

For the wave to line up, each row has to start a little later than the one above it. Short chains of registers on the edges of the array, called skews, delay row r by r cycles, so every value reaches a PE at the same moment as the running total it belongs to.

Three dataflows, one array

There are three common ways to run a matrix multiply on a systolic array, named after what stays in place inside each PE:

  • Weight stationary: each PE holds one weight while the inputs stream past it.
  • Input stationary: each PE holds one input while the weights stream past it.
  • Output stationary: both matrices stream through, and each PE builds up one result in place.

Each PE has a few multiplexers that choose where its second number comes from and what the product is added to, so the same hardware runs all three. Weight and input stationary turn out to be identical inside the PE; the only difference is which matrix goes to which edge of the array. Software picks the dataflow by writing a single register before each job.

Two precisions in the same hardware

Every value travels as a 16-bit word that holds either one 16-bit number or two 8-bit numbers side by side. In 8-bit mode each PE does two multiply-accumulates per cycle instead of one, which doubles the work the array gets through when 8 bits are precise enough, as they often are for neural networks.

The running totals are 36 bits wide, which leaves a few spare bits so they don't overflow. In 8-bit mode the adder is split down the middle and the carry between the two halves is cut, so one 8-bit result can never spill into the other.

Around the array

The array needs a new value on every row each cycle. Two operand buffers, A and B, are built from the FPGA's block RAM with one bank for each row or column they feed, so all of them can be read at once. A load buffer holds the 16 values the PEs keep in place and copies them into every PE in a single cycle. A router sends each buffer to the right edge of the array for the chosen dataflow.

Results come out of the bottom of the array into an output buffer. Each column finishes one cycle after the column to its left, so each column gets its own write pointer, and the results still land in order. A state machine takes every job through the same steps: load the values that stay in place (or clear the totals), stream the data in, wait for the last values to get through the grid, shift the results out in output stationary, and signal that it's done.

Running it from software

The processor sees the whole accelerator as a 128 KB block of memory addresses, so a job is just a series of stores and loads:

  1. Store the two matrices into the buffers.
  2. Store the dataflow, precision and length into the configuration registers.
  3. Store a 1 to the start bit.
  4. Load the status register until it says done.
  5. Load the results from the output buffer.

While a job runs, the accelerator ignores writes to its settings and buffers, so nothing can change underneath it, and it refuses to start with an invalid setup. The firmware reads the array size from the accelerator when it starts, then breaks a matrix multiply of any size into tiles that fit the array.

A processor to drive it

To control the accelerator I wrote a single-cycle RISC-V core that runs all 40 instructions of the RV32I base instruction set. Every instruction is fetched, decoded, executed and written back in one clock cycle. A decoder turns each instruction into the control signals for the register file, the ALU, the branch comparator and the load/store unit. Anything outside RV32I stops the core with a fault flag instead of doing something unpredictable.

The FPGA's block RAM only reads on a clock edge, which would normally cost an extra cycle on every instruction fetch and every load. To keep everything at one cycle, the instruction memory is given the address of the next instruction ahead of time, and the data memory works on the falling edge of the clock, halfway through the cycle.

What the numbers show

On a 16×16×16 matrix multiply, the full system finishes 17.6 times faster than the processor doing the same work in software (RV32I has no multiply instruction, so software multiplies with shifts and adds). The surprise is that the array itself is busy for only 432 of the 24,432 cycles. Nearly all the time goes into moving data in and out of the accelerator one 32-bit word at a time. The next step would be a DMA engine that moves the data on its own, so the processor stops being the bottleneck.

Verification

I checked the design at four levels in ModelSim: the array on its own, the accelerator driven through its addresses, the processor instruction by instruction, and the whole system running firmware. Every testbench compares the hardware with a reference I wrote separately from the RTL, and I planted bugs on purpose to make sure the tests would catch them.
